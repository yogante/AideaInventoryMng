## 2. 共通処理

### 2.1 トランザクション

- 原則として、1リクエストの更新処理を1トランザクションで実行する。
- 在庫数量、引当数量、在庫変動履歴、棚卸状態など、関連する更新はすべて同一トランザクション内で行う。
- いずれかの処理に失敗した場合は、当該リクエスト内の更新をすべてロールバックする。
- EF Coreの`SaveChangesAsync`は、可能な限り1回にまとめる。
- `SaveChangesAsync`を複数回実行する必要がある場合は、明示的なトランザクションで囲み、全処理の成功・失敗を一体として扱う。
- 読み取りのみの処理では、原則として更新用トランザクションを開始しない。
- 行ロックを取得する処理では、ロック取得から状態確認、データ更新、保存までを同一トランザクション内で実行する。

### 2.2 入力検証

- リクエストの形式や範囲（必須、桁数、数量が1以上など）はDTOの属性等で検証する。
- 入力形式・範囲の誤りは400（`VALIDATION_ERROR`）とする。
- レコードの存在、状態、在庫数量、引当数量など、DBの状態に依存するチェックは業務処理内で行う。
- 実棚数量は0以上とし、負数は認めない。

### 2.3 例外処理

共通の例外処理（ミドルウェア）で、例外をAPI設計書に定めるエラー応答へ変換する。

| 例外 | 変換先 |
|---|---|
| 業務例外（エラーコードとHTTPステータスを持つ） | 指定されたコードとステータス |
| EF Coreの同時実行例外 | 競合内容に応じて409（`VERSION_CONFLICT`） |
| ユニーク制約違反 | マスタ登録時は409（`DUPLICATE_CODE`）。在庫行の初回作成時は競合として再試行を検討 |
| 想定外の例外 | 500。詳細はログに記録し、応答には汎用メッセージを返す |

- 同時実行例外やユニーク制約違反は、発生した処理の内容に応じてエラーコードを判断する。
- 想定外の例外を業務エラーとして返さない。
- 実装で採用しているエラー応答形式（`code`、`message`等）とAPI設計書の形式を一致させる。

### 2.4 排他制御と再試行

#### 2.4.1 楽観的排他制御

- `version`を持つテーブルは、更新時に取得時点の`version`を条件として更新する（EF Coreの同時実行トークン）。
- 対象テーブルは`products`、`warehouses`、`locations`、`stocks`、`stocktakes`とする。
- クライアントが`version`を送信するAPI（マスタのPUT、棚卸の確定・中止）では、送信された`version`と現在の値が異なる場合、原則として再試行せず409（`VERSION_CONFLICT`）を返す。
- 棚卸ヘッダーの状態変更（DRAFTからIN_PROGRESS、IN_PROGRESSからCOMPLETEDまたはCANCELLED）でも`version`を更新する。
- `version`の加算は共通処理または各Serviceのいずれか一方で行う。二重に加算しないよう、実装上の責務を統一する。
- 行ロックと楽観的排他制御を併用する場合は、それぞれの役割を明確にし、同一の競合を二重に処理しないようにする。

#### 2.4.2 サーバー側での再試行

- クライアントが`version`を送信しない在庫更新処理（入庫、出庫、引当、引当解除、在庫移動）で競合が発生した場合は、競合の種類に応じて再試行を検討する。
- 再試行の対象は、在庫行の同時更新や在庫行の初回作成時のユニーク制約違反など、最新データを読み直して再実行することで解消できる競合に限定する。
- 再試行の上限は最大3回とする（案）。解消しない場合は409（`VERSION_CONFLICT`）を返す。
- 入力不正、在庫不足、棚卸中、状態不正など、再実行しても解消しない業務エラーは再試行しない。
- 再試行する場合は、失敗したトランザクションを終了し、新しいトランザクションで処理を最初から実行する。
- 失敗したトランザクション内でそのまま処理を続けない。
- PostgreSQLの行ロックを取得する処理では、ロックにより競合を直列化する。行ロックによって処理が直列化される場合は、不要な再試行を行わない。
- ユニーク制約違反を再試行する場合は、在庫行の初回作成時に発生した競合であることを確認する。マスタのコード重複など、再試行で解消しないエラーは再試行しない。

### 2.5 共通の更新項目

`SaveChangesAsync`の共通処理で、次の項目を設定する。

| タイミング | 設定する項目 |
|---|---|
| 追加時 | `created_at`（現在日時）。`created_by`は現状NULL |
| 更新時 | `updated_at`（現在日時）。`version`を持つテーブルは`version`を+1。`updated_by`は現状NULL |

- 日時はUTCで扱う。
- 楽観的排他制御の対象テーブルは、`products`、`warehouses`、`locations`、`stocks`、`stocktakes`とする。
- `version`の加算処理は、共通処理または各Serviceのどちらか一方に集約する。
- 棚卸明細（`stocktake_lines`）は、現時点では`version`による排他制御を行わない。実棚数量の更新時は棚卸ヘッダー行のロックで直列化する。
- 在庫変動履歴（`stock_movements`）は追加のみとし、`created_at`を設定する。原則として登録後の更新・削除は行わない。
- EF Coreの同時実行トークン設定と`version`の加算処理が二重にならないよう、DB列・モデル設定・共通更新処理の実装を統一する。

### 2.6 論理削除の扱い

- マスタの通常検索・参照は、`deleted_at`がNULLの行だけを対象とする。
- EF Coreのグローバルクエリフィルターを使用する（案）。
- 在庫変動履歴など過去の業務記録を参照する処理では、必要に応じて`IgnoreQueryFilters()`を使用し、削除済みマスタに関連する履歴も参照できるようにする。
- 論理削除したマスタのコードは、削除済みデータを含めて一意とし、再利用しない。
- 行ロックを取得する処理では、ロック取得後に対象データが論理削除されていないことを再確認する。

### 2.7 棚卸中チェックと排他制御（共通）

対象倉庫に、実施中の棚卸（`stocktakes.warehouse_id`が一致し、`status`が`IN_PROGRESS`）が存在するかを確認する。

棚卸中の場合、対象倉庫の在庫数量・引当数量に影響する処理を制限し、409（`STOCKTAKE_IN_PROGRESS`）を返す。

対象となる処理：

- 入庫
- 出庫
- 引当
- 引当解除
- 在庫移動（移動元・移動先の両方）

引当・引当解除は在庫数量そのものを変更しないが、棚卸中の在庫状態を一貫させるため、棚卸中は実行不可とする。

#### 2.7.1 ロケーション行のロック

棚卸開始と在庫更新処理が同時に実行されても、帳簿数量と在庫数量に不整合が発生しないよう、PostgreSQLの`SELECT ... FOR UPDATE`を使用する。

- 在庫数量・引当数量に影響する処理は、対象ロケーション行をロックしてから棚卸中チェックを行う。
- ロケーション行のロック取得後、対象ロケーションが存在し、論理削除されていないことを再確認する。
- 棚卸開始処理は、対象倉庫のロケーション行をロケーションIDの昇順でロックしてから、棚卸明細の作成と状態変更を行う。
- 在庫移動など複数ロケーションを扱う処理では、ロケーションIDの昇順でロックする。
- ロックの取得、棚卸中チェック、在庫更新は同一トランザクション内で行う。

棚卸開始と在庫更新処理が同じロケーション行をロックすることで、どちらか一方の処理が完了するまで、もう一方の処理は待機する。これにより、棚卸開始時の帳簿数量取得と在庫更新が同時に実行されることを防ぐ。

#### 2.7.2 倉庫行のロック

倉庫にロケーションが1件も存在しない場合、ロケーション行をロックしても排他制御が成立しない。また、棚卸開始とロケーション追加が同時に実行されると、棚卸対象に含まれないロケーションが作成される可能性がある。

このため、次の処理では倉庫行のロックを使用する方針とする（実装確認が必要）。

- 棚卸開始処理
- 棚卸明細追加処理
- ロケーションの新規登録処理
- 棚卸確定処理
- 棚卸中止処理
- 同一倉庫の棚卸ヘッダー作成処理（同一倉庫での棚卸重複作成を防ぐ場合）

倉庫行ロックを使用する処理では、対象倉庫行を先にロックし、対象倉庫が存在し、論理削除されていないことを確認する。

ロケーション新規登録処理も倉庫行をロックし、対象倉庫で棚卸がIN_PROGRESSではないことを確認してから登録する。

対象処理間で取得順序を統一する。ロケーション行をロックする処理が、後から倉庫行をロックすることは避ける。

#### 2.7.3 棚卸確定・中止時のロック

- 棚卸確定処理では、対象倉庫行をロックする。
- 対象倉庫のロケーション行をロケーションIDの昇順でロックする。
- その後、棚卸ヘッダー行をロックする。
- 棚卸確定処理では、続いて対象となる在庫行を在庫IDの昇順でロックする。
- ロケーション行・棚卸ヘッダー行・在庫行のロック、在庫数量の確認・更新、在庫調整履歴の登録、棚卸状態の更新は同一トランザクション内で行う。
- 棚卸中止処理でも、対象倉庫行、対象倉庫のロケーション行、棚卸ヘッダー行の順にロックして状態を変更する。

#### 2.7.4 棚卸関連処理のロック取得順序

デッドロックを防ぐため、棚卸関連処理では原則として次の順序でロックを取得する。

1. 倉庫行（倉庫IDの昇順）
2. 対象ロケーション行（ロケーションIDの昇順）
3. 棚卸ヘッダー行
4. 対象在庫行（在庫IDの昇順）

棚卸ヘッダーから倉庫IDを取得する場合は、最初にロックを取得しない読み取りを行う。その後、上記の順序でロックを取得し、ヘッダーの状態や`version`を再確認する。

実棚数量の更新処理は棚卸ヘッダー行のみをロックする。この処理ではロケーション行や在庫行のロックを後から取得しない。

棚卸明細追加処理では、倉庫行、対象ロケーション行、棚卸ヘッダー行の順にロックする。

#### 2.7.5 在庫更新処理のロック取得順序

入庫、出庫、引当、引当解除では、次の順序でロックを取得する。

1. 対象ロケーション行
2. 対象在庫行

在庫移動では、次の順序でロックを取得する。

1. 移動元・移動先の倉庫行（倉庫IDの昇順。複数倉庫にまたがる場合）
2. 移動元・移動先のロケーション行（ロケーションIDの昇順）
3. 移動元・移動先の在庫行（在庫IDの昇順）

ロケーション行をロックした後、棚卸中チェックを行い、対象ロケーションの状態を再確認する。

複数のロケーション・在庫行を扱う場合は、必ず同じ順序でロックを取得する。

### 2.8 ログ

- 構造化ログを標準出力に出力する（AWSではCloudWatch Logsで確認する）。
- 更新系処理は、処理名、対象ID、結果（成功、業務エラー、競合）を記録する。
- 想定外の例外は、スタックトレースを含めて記録する。
- パスワード、接続文字列、認証情報などの機密情報はログに出力しない。

## 4. 処理詳細

### 4.1 P01 入庫

#### 手順

1. 入力を検証する（数量は1以上など）。誤りは400。
2. 商品とロケーションの存在を確認する（削除済みは存在しない扱い）。存在しなければ404。
3. 対象ロケーション行をロックする。
4. ロック取得後、対象ロケーションが存在し、論理削除されていないことを再確認する。存在しなければ404。
5. ロケーションが属する倉庫について、棚卸中チェック（2.7）を行う。
6. 商品×ロケーションの在庫行を取得する。存在しなければ、数量0・引当数量0の行を新規作成する。
7. 在庫数量に入庫数量を加算する。
8. 在庫変動履歴を追加する。
9. 保存する（2.1、2.4）。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocks` | 追加または更新 | `quantity` += 入庫数量 |
| `stock_movements` | 追加 | `movement_type` = `RECEIPT`、`quantity_change` = +入庫数量、`occurred_at` = 指定値（未指定なら現在日時）、`remarks` |

#### エラー

400、404、409（`STOCKTAKE_IN_PROGRESS`、`VERSION_CONFLICT`）

### 4.2 P02 出庫

#### 手順

1. 入力を検証する。
2. 商品とロケーションの存在を確認する。存在しなければ404。
3. 対象ロケーション行をロックする。
4. ロック取得後、対象ロケーションが存在し、論理削除されていないことを再確認する。存在しなければ404。
5. 棚卸中チェック（2.7）を行う。
6. 在庫行を取得する。存在しなければ在庫0として扱い、409（`INSUFFICIENT_STOCK`）。
7. 出庫可能な数量を確認する。
   - `useReservation`がfalse（既定）の場合：引当可能数（在庫数量－引当数量）以内であること。
   - `useReservation`がtrueの場合（案）：引当数量以内であること。
   - 数量を超えていれば409（`INSUFFICIENT_STOCK`）。
8. 在庫を更新する。
9. 在庫変動履歴を追加する。
10. 保存する。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocks` | 更新 | `quantity` -= 出庫数量。`useReservation`がtrueの場合は`reserved_quantity`も同じ数量だけ減らす（案） |
| `stock_movements` | 追加 | `movement_type` = `ISSUE`、`quantity_change` = −出庫数量 |

#### エラー

400、404、409（`INSUFFICIENT_STOCK`、`STOCKTAKE_IN_PROGRESS`、`VERSION_CONFLICT`）

※ `useReservation`の有無・仕様は、現行の出庫API実装を確認して確定する。

### 4.3 P03 引当

#### 手順

1. 入力を検証する。
2. 商品とロケーションの存在を確認する。存在しなければ404。
3. 対象ロケーション行をロックする。
4. ロック取得後、対象ロケーションが存在し、論理削除されていないことを再確認する。存在しなければ404。
5. 棚卸中チェック（2.7）を行う。
6. 在庫行を取得する。存在しなければ在庫0として扱い、409（`INSUFFICIENT_STOCK`）。
7. 引当数量が引当可能数（在庫数量－引当数量）以内であることを確認する。超えていれば409（`INSUFFICIENT_STOCK`）。
8. 引当数量を加算して保存する。

#### 更新内容

`stocks.reserved_quantity` += 引当数量。引当・引当解除は在庫変動履歴に記録しない。

### 4.4 P04 引当解除

#### 手順

1. 入力を検証する。
2. 商品とロケーションの存在を確認する。存在しなければ404。
3. 対象ロケーション行をロックする。
4. ロック取得後、対象ロケーションが存在し、論理削除されていないことを再確認する。存在しなければ404。
5. 棚卸中チェック（2.7）を行う。
6. 在庫行を取得する。存在しなければ409（`INSUFFICIENT_RESERVATION`）。
7. 解除数量が引当数量以内であることを確認する。超えていれば409（`INSUFFICIENT_RESERVATION`）。
8. 引当数量を減算して保存する。

#### 更新内容

`stocks.reserved_quantity` −= 解除数量。在庫変動履歴には記録しない。

### 4.5 P05 在庫移動

#### 手順

1. 入力を検証する（移動元と移動先が同じ場合は400）。
2. 商品、移動元ロケーション、移動先ロケーションの存在を確認する。存在しなければ404。
3. 移動元・移動先の倉庫行を倉庫IDの昇順でロックする。移動元と移動先が同じ倉庫の場合は1回とする。
4. ロック取得後、対象倉庫が存在し、論理削除されていないことを再確認する。
5. 移動元と移動先のロケーション行をロケーションIDの昇順でロックする。
6. ロック取得後、移動元と移動先のロケーションが存在し、論理削除されていないことを再確認する。存在しなければ404。
7. 移動元と移動先の倉庫について、それぞれ棚卸中チェック（2.7）を行う。同じ倉庫の場合は1回とする。
8. 移動元の在庫行を取得し、引当可能数が移動数量以上であることを確認する。足りなければ409（`INSUFFICIENT_STOCK`）。
9. 移動元・移動先の在庫行を在庫IDの昇順でロックする。移動先の在庫行が存在しなければ、数量0・引当数量0の行を新規作成する。
10. 移動元の在庫数量を減らし、移動先の在庫数量を増やす。
11. 移動番号を採番する（方法は未決。シーケンスを使う案）。
12. 在庫変動履歴を2行追加する。
13. 保存する（1つのトランザクション）。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocks`（移動元） | 更新 | `quantity` −= 移動数量 |
| `stocks`（移動先） | 追加または更新 | `quantity` += 移動数量 |
| `stock_movements` | 追加（2行） | 移動元：`TRANSFER_OUT`、−移動数量。移動先：`TRANSFER_IN`、+移動数量。両方に同じ`transfer_no`を設定 |

#### エラー

400、404、409（`INSUFFICIENT_STOCK`、`STOCKTAKE_IN_PROGRESS`、`VERSION_CONFLICT`）

### 4.6 P06 棚卸ヘッダーの作成

**対応API：** POST `/api/stocktakes`

#### 手順

1. 入力を検証する（`warehouseId`、`stocktakeDate`など）。
2. 対象倉庫の存在を確認する。存在しなければ404（`NOT_FOUND`）。
3. 対象倉庫行をロックする。
4. ロック取得後、対象倉庫が存在し、論理削除されていないことを再確認する。
5. 同じ倉庫に`IN_PROGRESS`の棚卸が存在しないことを確認する。存在する場合は409（`STOCKTAKE_IN_PROGRESS`）。
6. 棚卸ヘッダーを追加する。状態は`DRAFT`とする。
7. 保存する。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocktakes` | 追加 | `warehouse_id`、`stocktake_date`、`remarks`、`status` = `DRAFT`、`version` |

この処理では、棚卸明細の作成や在庫数量の固定は行わない。

#### 排他制御

- 倉庫行をロックしてから、同一倉庫の棚卸状態を確認する。
- 同一倉庫の棚卸ヘッダー作成・開始処理を直列化する。
- 倉庫行ロックから棚卸ヘッダーの追加までを同一トランザクションで行う。

#### エラー

400、404（`NOT_FOUND`）、409（`STOCKTAKE_IN_PROGRESS`）

※ 同じ倉庫にIN_PROGRESSの棚卸が存在する場合に、新しいDRAFTの作成まで禁止するかは未決事項とする。現状は既存仕様を維持し、API設計書と合わせて確定する。

### 4.7 P07 棚卸の開始

**対応API：** POST `/api/stocktakes/{id}/start`

#### 手順

1. 棚卸ヘッダーを取得する（ロックなし）。存在しなければ404（`NOT_FOUND`）。
2. 対象倉庫行をロックする。
3. 対象倉庫が存在し、論理削除されていないことを確認する。
4. 対象倉庫のロケーション行をロケーションIDの昇順でロックする。
5. 棚卸ヘッダー行をロックし、最新の状態を読み直す。
6. ヘッダーの倉庫IDが最初に取得した倉庫IDと一致することを確認する。
7. 状態が`DRAFT`であることを確認する。違えば409（`INVALID_STOCKTAKE_STATUS`）。
8. 同じ倉庫に別の`IN_PROGRESS`の棚卸が存在しないことを確認する。存在する場合は409（`STOCKTAKE_IN_PROGRESS`）。
9. 対象倉庫の在庫行を取得する。
10. 在庫行ごとに棚卸明細を作成する。
11. 棚卸状態を`IN_PROGRESS`に変更する。
12. 明細作成と状態変更を同一トランザクションで保存する。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocktake_lines` | 追加（複数行） | `stock_id` = 対象在庫ID、`product_id`、`location_id`、`book_quantity` = 棚卸開始時点の在庫数量、`actual_quantity` = NULL、`difference_quantity` = NULL |
| `stocktakes` | 更新 | `status` = `IN_PROGRESS`、`version`を更新 |

棚卸開始時点の在庫数量を`book_quantity`に保存する。棚卸明細の`stock_id`には、開始時点の在庫IDを保存する。

#### 排他制御

- 倉庫行、対象ロケーション行、棚卸ヘッダー行の順にロックする。
- 入庫・出庫・引当・引当解除・在庫移動は、対象ロケーション行をロックしてから棚卸中チェックを行う。
- ロックの取得から棚卸明細の作成、棚卸状態の変更までを同一トランザクションで行う。
- ロケーション行が0件の場合も、倉庫行ロックによってロケーション追加処理と直列化する。
- ロケーション追加処理も倉庫行ロックを使用すること。

#### エラー

404（`NOT_FOUND`）、409（`INVALID_STOCKTAKE_STATUS`、`STOCKTAKE_IN_PROGRESS`）

### 4.8 P08 棚卸明細の追加

**対応API：** POST `/api/stocktakes/{id}/lines`

#### 手順

1. 棚卸ヘッダーを取得する（ロックなし）。存在しなければ404（`NOT_FOUND`）。
2. 棚卸ヘッダーから対象倉庫IDを取得する。
3. 対象倉庫行をロックする。
4. 対象倉庫が存在し、論理削除されていないことを確認する。
5. 対象ロケーション行をロックする。
6. ロケーションが存在し、論理削除されていないことを確認する。
7. 棚卸ヘッダー行をロックし、最新の状態を読み直す。
8. ヘッダーの倉庫IDが最初に取得した倉庫IDと一致することを確認する。
9. 状態が`IN_PROGRESS`であることを確認する。違えば409（`INVALID_STOCKTAKE_STATUS`）。
10. 商品とロケーションの存在を確認する。存在しなければ404（`NOT_FOUND`）。
11. ロケーションが棚卸対象倉庫に属していることを確認する。
12. 同じ商品・ロケーションの棚卸明細が存在しないことを確認する。存在する場合は409（`DUPLICATE_STOCKTAKE_LINE`）。
13. 同じ商品・ロケーションの在庫行が存在しないことを確認する。存在する場合は409（`STOCK_ALREADY_EXISTS`）。
14. 棚卸明細を追加する。
15. 保存する。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocktake_lines` | 追加 | `stock_id` = NULL、`product_id`、`location_id`、`book_quantity` = 0、`actual_quantity` = NULL、`difference_quantity` = NULL |

このAPIは、棚卸中に帳簿に存在しない在庫を発見した場合に使用する。追加した明細は新規在庫として扱う。この時点では在庫行の作成や在庫数量の更新は行わない。

#### 排他制御

- 倉庫行、対象ロケーション行、棚卸ヘッダー行の順にロックする。
- 棚卸確定・中止処理と同じ棚卸ヘッダー行をロックすることで、明細追加と確定・中止を直列化する。
- ロック取得から明細追加までを同一トランザクションで行う。

#### エラー

400、404（`NOT_FOUND`）、409（`INVALID_STOCKTAKE_STATUS`、`DUPLICATE_STOCKTAKE_LINE`、`STOCK_ALREADY_EXISTS`）

### 4.9 P09 実棚数量の入力・更新

**対応API：** PUT `/api/stocktakes/{id}/lines/{lineId}`

#### 手順

1. 入力を検証する。実棚数量は0以上とする。負数の場合は400（`INVALID_ACTUAL_QUANTITY`）。
2. 棚卸ヘッダーを取得する。存在しなければ404（`NOT_FOUND`）。
3. 棚卸ヘッダー行をロックし、最新の状態を読み直す。
4. 棚卸状態が`IN_PROGRESS`であることを確認する。違えば409（`INVALID_STOCKTAKE_STATUS`）。
5. 棚卸明細を取得する。指定した棚卸に属していなければ404（`NOT_FOUND`）。
6. 実棚数量を更新する。
7. 差異数量を計算する（実棚数量－帳簿数量）。
8. 保存する。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocktake_lines` | 更新 | `actual_quantity` = 入力された実棚数量 |
| `stocktake_lines` | 更新 | `difference_quantity` = 実棚数量 − 帳簿数量 |

実棚数量が0の場合も登録可能とする。このAPIでは在庫数量を更新しない。在庫数量の更新と在庫調整履歴の登録は棚卸確定処理で行う。

#### 排他制御

- 棚卸ヘッダー行をロックしてから、状態が`IN_PROGRESS`であることを確認する。
- 棚卸確定・中止処理も同じ棚卸ヘッダー行をロックする。
- 棚卸ヘッダーのロック取得から実棚数量・差異数量の更新までを同一トランザクションで行う。
- この処理ではロケーション行や在庫行のロックを取得しない。

これにより、実棚数量の更新と棚卸確定・中止処理を直列化する。

#### エラー

400（`VALIDATION_ERROR`、`INVALID_ACTUAL_QUANTITY`）、404（`NOT_FOUND`）、409（`INVALID_STOCKTAKE_STATUS`）

### 4.10 P10 棚卸の確定

**対応API：** POST `/api/stocktakes/{id}/complete`

#### 手順

1. 棚卸ヘッダーを取得する（ロックなし）。存在しなければ404（`NOT_FOUND`）。
2. 対象倉庫IDを取得する。
3. 対象倉庫行をロックする。
4. 対象倉庫のロケーション行をロケーションIDの昇順でロックする。
5. 棚卸ヘッダー行をロックする。
6. ヘッダーの倉庫IDが最初に取得した倉庫IDと一致することを確認する。
7. リクエストの`version`と現在の棚卸ヘッダーの`version`を比較する。一致しなければ409（`VERSION_CONFLICT`）。
8. 状態が`IN_PROGRESS`であることを確認する。違えば409（`INVALID_STOCKTAKE_STATUS`）。
9. すべての棚卸明細に実棚数量が入力されていることを確認する。未入力があれば409（`ACTUAL_QUANTITY_NOT_ENTERED`）。
10. 棚卸明細に対応する既存在庫行を在庫IDの昇順でロックする。
11. 各明細について、差異数量を確認する。
12. `stock_id`の有無によって、既存在庫と新規在庫の処理を分ける。
13. 在庫数量の更新、新規在庫行の作成、在庫変動履歴の登録を行う。
14. 棚卸状態を`COMPLETED`に変更し、確定日時を設定する。
15. すべての処理を同一トランザクションで保存する。

#### 既存在庫の更新（stock_idあり）

- 現在の在庫数量が棚卸開始時点の帳簿数量（`book_quantity`）と一致することを確認する。
- 一致しない場合は409（`STOCKTAKE_QUANTITY_CONFLICT`）を返す。
- 実棚数量が現在の引当数量を下回る場合は409（`RESERVED_QUANTITY_CONFLICT`）を返す。
- 在庫数量を実棚数量に更新する。
- 引当数量は変更しない。
- `stock_id`が参照する在庫の`product_id`・`location_id`が棚卸明細の値と一致することをアプリケーション側で確認する。

#### 新規在庫の登録（stock_idなし）

- 同じ商品・ロケーションの在庫行が既に存在しないことを確認する。
- 既に存在する場合は409（`STOCK_ALREADY_EXISTS`）を返す。
- 実棚数量が1以上の場合は、在庫行を新規作成する。
- 新規在庫の引当数量は0とする。
- 実棚数量が0の場合は、在庫行を作成しない。

#### 在庫調整履歴

- 差異数量が0以外の場合、在庫変動履歴に`STOCKTAKE_ADJUST`を登録する。
- 履歴の`quantity_change`には差異数量を設定する。
- 差異数量が0の場合は在庫調整履歴を登録しない。
- 新規在庫の場合も、実棚数量が1以上であれば帳簿数量0からの増加として履歴を登録する。

#### 更新内容

| テーブル | 操作 | 内容 |
|---|---|---|
| `stocks` | 更新 | 既存在庫の`quantity` = 実棚数量 |
| `stocks` | 追加 | 新規在庫の`product_id`、`location_id`、`quantity` = 実棚数量、`reserved_quantity` = 0 |
| `stock_movements` | 追加 | `movement_type` = `STOCKTAKE_ADJUST`、`quantity_change` = 差異数量 |
| `stocktakes` | 更新 | `status` = `COMPLETED`、`completed_at` = 現在日時、`version`を更新 |

上記の処理はすべて同一トランザクションで実行する。途中でエラーが発生した場合は、在庫数量・在庫行・履歴・棚卸状態のすべてをロールバックする。

#### 排他制御

- 倉庫行、ロケーション行、棚卸ヘッダー行、在庫行の順にロックする。
- 既存在庫行は在庫IDの昇順でロックする。
- `stock_id`がNULLの明細については、同じ商品・ロケーションの在庫行が存在しないことを確定直前に再確認する。
- 在庫行の初回作成時にユニーク制約違反が発生した場合は、競合の内容を確認する。必要に応じてトランザクションを終了し、再試行する。
- ロック取得から在庫更新、履歴登録、棚卸状態の更新までを同一トランザクションで行う。

#### エラー

- 400（`VALIDATION_ERROR`）
- 404（`NOT_FOUND`）
- 409（`VERSION_CONFLICT`）
- 409（`INVALID_STOCKTAKE_STATUS`）
- 409（`ACTUAL_QUANTITY_NOT_ENTERED`）
- 409（`STOCKTAKE_QUANTITY_CONFLICT`）
- 409（`RESERVED_QUANTITY_CONFLICT`）
- 409（`STOCK_ALREADY_EXISTS`）

### 4.11 P11 棚卸の中止

**対応API：** POST `/api/stocktakes/{id}/cancel`

#### 手順

1. 棚卸ヘッダーを取得する（ロックなし）。存在しなければ404（`NOT_FOUND`）。
2. 対象倉庫IDを取得する。
3. 対象倉庫行をロックする。
4. 対象倉庫のロケーション行をロケーションIDの昇順でロックする。
5. 棚卸ヘッダー行をロックする。
6. ヘッダーの倉庫IDが最初に取得した倉庫IDと一致することを確認する。
7. リクエストの`version`と現在の棚卸ヘッダーの`version`を比較する。一致しなければ409（`VERSION_CONFLICT`）。
8. 状態が`IN_PROGRESS`であることを確認する。違えば409（`INVALID_STOCKTAKE_STATUS`）。

### 4.12 P12～P14 商品・倉庫・ロケーションの削除

#### 手順

1. 対象を取得する。存在しない、または削除済みの場合は404。
2. 対象に応じて必要な行ロックを取得する。
   - 商品の場合は、現行案では商品行ロックを取得しない。
   - ロケーションの場合は、対象倉庫行を先にロックし、対象ロケーション行をロケーションID順でロックする。
   - 倉庫の場合は、倉庫行を先にロックし、その倉庫に属するすべてのロケーション行をロケーションIDの昇順でロックする。
3. ロック取得後、対象データが存在し、論理削除されていないことを再確認する。
4. 倉庫・ロケーションの場合は、対象倉庫にIN_PROGRESSの棚卸が存在しないことを確認する。存在する場合は409（`STOCKTAKE_IN_PROGRESS`）。
5. 商品・ロケーション・倉庫に関連する在庫行を確認する。対象に、在庫数量または引当数量が0でない在庫行があれば409（`HAS_STOCK`）。
   - 商品：その商品の在庫行
   - ロケーション：そのロケーションの在庫行
   - 倉庫：その倉庫に属するロケーションの在庫行
6. `deleted_at`に現在日時を設定して保存する。

在庫数量・引当数量がともに0の在庫行は、履歴との整合性を保つため、そのまま残す。

#### 補足

- ロケーション・倉庫の削除は、在庫更新処理とロケーション行ロックで直列化する。
- 倉庫削除時は、倉庫行とロケーション行のロック取得順序を統一する。
- 倉庫・ロケーションは棚卸中に削除しない。棚卸対象となるロケーション構成を変更しないため、409（`STOCKTAKE_IN_PROGRESS`）とする。
- 商品の削除は行ロックを取得しない。削除と入庫がごく短い間に重なった場合の制約は5.1に記載する。
- 商品削除と入庫の同時実行に対する排他制御は、今後の改善対象とする。

### 4.13 P15 マスタの登録・更新

#### 登録

1. 入力を検証する。
2. ロケーションの場合は、倉庫行をロックする。
3. 対象倉庫が存在し、論理削除されていないことを確認する。存在しなければ404。
4. ロケーションの場合は、対象倉庫で棚卸がIN_PROGRESSではないことを確認する。棚卸中の場合は409（`STOCKTAKE_IN_PROGRESS`）。
5. コードの重複を確認する（削除済みも含む。ロケーションは同じ倉庫内）。重複なら409（`DUPLICATE_CODE`）。
6. 追加して保存する。同時登録でユニーク制約に違反した場合も409（`DUPLICATE_CODE`）。

#### 更新

1. 入力を検証する。
2. 対象を取得する。存在しなければ404。
3. 対象行を更新するため、取得時の`version`を使った楽観的排他制御を行う。
4. 送信された`version`と現在の値が異なる場合は409（`VERSION_CONFLICT`）。
5. コード（ロケーションは倉庫も）は変更せず、それ以外の項目を更新して保存する（案）。

### 4.14 P16 在庫の照会・集計

- 検索条件に応じて`stocks`を検索する。
- 引当可能数は、在庫数量－引当数量で求める。
- 集計は、`groupBy`が`product`なら商品ごとに全倉庫を合算し、`warehouse`なら商品×倉庫ごとにロケーションを合算する。
- 削除済みの商品・ロケーションに関連する在庫行は、結果に含めない（案）。
- 読み取り処理のため、在庫更新用の行ロックは原則として取得しない。
- 読み取り中に在庫が更新される場合の整合性は、DBのトランザクション分離レベルに従う。

### 4.15 P17 在庫下限アラートの検出

#### 手順

1. 削除されておらず、在庫下限数量が設定されている商品を対象にする。
2. 商品ごとに、全倉庫の在庫数量を合計する。在庫行がない商品は0とする。
3. 合計が在庫下限数量を下回る商品を返す。不足数は「在庫下限数量－合計」とする。
4. 並び順は、不足数の大きい順とする（案）。

### 4.16 P18 CSV出力

- 対応する検索APIと同じ絞り込み条件・並び順で、ページングを行わずに全件を出力する。
- 文字コードはUTF-8（BOM付き）とし、ヘッダー行を付ける（案）。
- 件数が多い場合に備え、ストリーミングで返す（案）。
- CSV出力中にデータが更新された場合の扱い（出力開始時点のスナップショットとするか等）は、実装時に決定する。

### 4.17 P19 在庫変動履歴の照会

**対応API：**

- GET `/api/stock-movements`
- GET `/api/stock-movements/{id}`

#### 一覧取得

1. クエリパラメーター（商品、倉庫、ロケーション、変動種別、期間、ページ、ページサイズ）を検証する。
2. 在庫変動履歴を検索する。
3. 必要に応じて商品・ロケーション・倉庫情報を結合する。
4. 発生日時の降順、同一日時の場合はIDの降順で並べる。
5. ページングして返す。

#### 詳細取得

1. 履歴IDを指定して在庫変動履歴を取得する。
2. 商品、ロケーション、倉庫などの表示情報を取得する。
3. 該当データがなければ404（`NOT_FOUND`）を返す。
4. 該当データがあれば詳細情報を返す。

#### 補足

- 履歴は原則として追加のみで、更新・削除しない。
- 商品・倉庫・ロケーションが論理削除済みでも、過去の履歴を参照できるようにする。
- 引当・引当解除は在庫変動履歴に記録しない。
- 入庫・出庫・在庫移動・棚卸差異調整は在庫変動履歴に記録する。

## 5. 既知の制約と未決事項

### 5.1 既知の制約

| 項目 | 内容 |
|---|---|
| 棚卸明細の実棚数量更新 | 明細単位の`version`による排他制御は行わない。棚卸ヘッダー行をロックし、状態が`IN_PROGRESS`であることを確認して更新する |
| 在庫更新と棚卸開始の排他制御 | 対象ロケーション行を使用する。ロック取得から更新まで同一トランザクションで実行する |
| 棚卸確定時の排他制御 | 倉庫行、ロケーション行（ロケーションID昇順）、棚卸ヘッダー行、在庫行（在庫ID昇順）の順にロックする |
| 棚卸中止時の排他制御 | 倉庫行、ロケーション行（ロケーションID昇順）、棚卸ヘッダー行の順にロックする |
| 棚卸明細追加時の排他制御 | 倉庫行、対象ロケーション行、棚卸ヘッダー行の順にロックする |
| 在庫移動時の排他制御 | 複数倉庫の場合は倉庫ID昇順、複数ロケーションの場合はロケーションID昇順、在庫行は在庫ID昇順でロックする |
| 再試行の上限 | 競合時の再試行は最大3回（案）。対象を在庫行の競合等に限定し、超えた場合は409を返す |
| 商品の削除と入庫の同時実行 | 商品の削除は行ロックを取得しない。削除の在庫チェックと入庫が短時間に重なると、削除済みの商品に在庫が残る可能性がある。今回は許容する |
| ロケーション追加と棚卸開始 | 棚卸開始時に対象ロケーションが0件の場合や、ロケーション追加が同時実行される場合の競合を防ぐため、倉庫行ロックを導入する方針。実装確認が必要 |
| 倉庫・ロケーションの削除 | 棚卸中の倉庫・ロケーション削除は禁止する方針。実装確認が必要 |
| 認証・権限 | 現時点では対象外とする |
