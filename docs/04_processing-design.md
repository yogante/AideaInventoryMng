## 2. 共通処理

### 2.1 トランザクション
- 1リクエスト = 1トランザクションとする
- データを更新する処理は、`SaveChanges` を1回にまとめ、在庫・履歴・状態の更新がすべて成功するか、すべて失敗するかのどちらかにする
- 処理を複数回の保存に分ける必要がある場合は、明示的なトランザクションで囲む

### 2.2 入力検証
- リクエストの形式と範囲(必須、桁数、1以上など)は、DTOの属性で検証する。誤りは400(`VALIDATION_ERROR`)
- 存在確認や在庫の過不足など、DBの状態に依存するチェックは、Servicesの中で行う(業務エラー)

### 2.3 例外処理
共通の例外処理(ミドルウェア)で、例外をAPI設計書2.4のエラー応答に変換する。

| 例外 | 変換先 |
|---|---|
| 業務例外(エラーコードとステータスを持つ) | そのコードとステータス |
| 同時更新の例外(EF Core) | 2.4の再試行後も解消しなければ409(`VERSION_CONFLICT`) |
| ユニーク制約違反 | マスタの登録では409(`DUPLICATE_CODE`)。在庫行の初回作成での競合は2.4の再試行 |
| 想定外の例外 | 500。詳細はログにだけ出し、応答には汎用のメッセージを返す |

### 2.4 排他制御と再試行
- 更新は、`version` を条件にして行う(EF Coreの同時実行トークン)
- **クライアントが `version` を送るAPI**(マスタのPUT、棚卸の確定・中止): 送られた `version` と現在の値が違えば、再試行せずに409(`VERSION_CONFLICT`)を返す
- **クライアントが `version` を持たない処理**(入庫・出庫・引当・引当解除・在庫移動): 競合したら、サーバー側で読み直して最初から処理をやり直す。最大3回(案)。それでも解消しなければ409(`VERSION_CONFLICT`)
- 在庫行の初回作成が同時に重なった場合(ユニーク制約違反)も、同じ再試行を行う

### 2.5 共通の更新項目
`SaveChanges` の共通処理で、次の項目を自動的に設定する。

| タイミング | 設定する項目 |
|---|---|
| 追加時 | `created_at`(現在日時)。`created_by` は現状NULL |
| 更新時 | `updated_at`(現在日時)。`version` を持つテーブルは `version` を+1。`updated_by` は現状NULL |

入出庫履歴は追加のみで、`created_at` だけを設定する。日時はすべてUTCで扱う。

### 2.6 論理削除の扱い
マスタの検索・参照は、`deleted_at` がNULLの行だけを対象にする(EF Coreのグローバルクエリフィルターを使う案)。

### 2.7 棚卸中チェック(共通)
倉庫IDを指定して、その倉庫に実施中の棚卸(`stocktakes` の `warehouse_id` が一致し、`status` が `IN_PROGRESS`)があるかを確認する。あれば409(`STOCKTAKE_IN_PROGRESS`)。

入庫、出庫、引当、引当解除、在庫移動(移動元と移動先の両倉庫)が、処理の最初に行う。

### 2.8 ログ
- 構造化ログを標準出力に出す(AWSではCloudWatch Logsで確認する)
- 更新系の処理は、処理名、対象のID、結果(成功、業務エラー、競合)を記録する
- 想定外の例外は、スタックトレースを含めて記録する

## 4. 処理詳細

### 4.1 P01 入庫

**手順**
1. 入力を検証する(数量は1以上など)。誤りは400
2. 商品とロケーションの存在を確認する(削除済みは存在しない扱い)。なければ404
3. ロケーションが属する倉庫について、棚卸中チェック(2.7)を行う
4. 商品 × ロケーションの在庫行を取得する。なければ、数量0・引当数量0の行を新規に作る
5. 在庫数量に入庫数量を加算する
6. 入出庫履歴を追加する
7. 保存する(2.1、2.4)

**更新内容**

| テーブル | 操作 | 内容 |
|---|---|---|
| stocks | 追加または更新 | `quantity` += 入庫数量 |
| stock_movements | 追加 | `movement_type` = RECEIPT、`quantity_change` = +入庫数量、`occurred_at` = 指定値(なければ現在日時)、`remarks` |

**エラー**: 400、404、409(`STOCKTAKE_IN_PROGRESS`、`VERSION_CONFLICT`)

### 4.2 P02 出庫

**手順**
1. 入力を検証する
2. 商品とロケーションの存在を確認する。なければ404
3. 棚卸中チェック(2.7)を行う
4. 在庫行を取得する。なければ在庫0として扱い、409(`INSUFFICIENT_STOCK`)
5. 出庫できる数量を確認する
   - `useReservation` がfalse(既定)のとき: 引当可能数(在庫数量 − 引当数量)以内であること
   - `useReservation` がtrueのとき(案): 引当数量以内であること
   - 超えていれば409(`INSUFFICIENT_STOCK`)
6. 在庫を更新する
7. 入出庫履歴を追加する
8. 保存する

**更新内容**

| テーブル | 操作 | 内容 |
|---|---|---|
| stocks | 更新 | `quantity` −= 出庫数量。`useReservation` がtrueのときは `reserved_quantity` も同じ数量だけ減らす(案) |
| stock_movements | 追加 | `movement_type` = ISSUE、`quantity_change` = −出庫数量 |

**エラー**: 400、404、409(`INSUFFICIENT_STOCK`、`STOCKTAKE_IN_PROGRESS`、`VERSION_CONFLICT`)

### 4.3 P03 引当

**手順**
1. 入力を検証する
2. 商品とロケーションの存在を確認する。なければ404
3. 棚卸中チェック(2.7)を行う
4. 在庫行を取得する。なければ在庫0として扱い、409(`INSUFFICIENT_STOCK`)
5. 引当数量が引当可能数(在庫数量 − 引当数量)以内であることを確認する。超えていれば409(`INSUFFICIENT_STOCK`)
6. 引当数量を加算して保存する

**更新内容**: `stocks.reserved_quantity` += 引当数量。入出庫履歴には記録しない。

### 4.4 P04 引当解除

**手順**
1. 入力を検証する
2. 商品とロケーションの存在を確認する。なければ404
3. 棚卸中チェック(2.7)を行う
4. 在庫行を取得する。なければ409(`INSUFFICIENT_RESERVATION`)
5. 解除数量が引当数量以内であることを確認する。超えていれば409(`INSUFFICIENT_RESERVATION`)
6. 引当数量を減算して保存する

**更新内容**: `stocks.reserved_quantity` −= 解除数量。入出庫履歴には記録しない。

### 4.5 P05 在庫移動

**手順**
1. 入力を検証する(移動元と移動先が同じなら400)
2. 商品、移動元ロケーション、移動先ロケーションの存在を確認する。なければ404
3. 移動元と移動先の倉庫について、それぞれ棚卸中チェック(2.7)を行う(同じ倉庫なら1回)
4. 移動元の在庫行を取得し、引当可能数が移動数量以上であることを確認する。足りなければ409(`INSUFFICIENT_STOCK`)
5. 移動先の在庫行を取得する。なければ、数量0・引当数量0の行を新規に作る
6. 移動元の在庫数量を減らし、移動先の在庫数量を増やす
7. 移動番号を採番する(方法は未決。シーケンスを使う案)
8. 入出庫履歴を2行追加する
9. 保存する(1つのトランザクション)

**更新内容**

| テーブル | 操作 | 内容 |
|---|---|---|
| stocks(移動元) | 更新 | `quantity` −= 移動数量 |
| stocks(移動先) | 追加または更新 | `quantity` += 移動数量 |
| stock_movements | 追加(2行) | 移動元: TRANSFER_OUT、−移動数量。移動先: TRANSFER_IN、+移動数量。どちらも同じ `transfer_no` |

**エラー**: 400、404、409(`INSUFFICIENT_STOCK`、`STOCKTAKE_IN_PROGRESS`、`VERSION_CONFLICT`)

### 4.6 P06 棚卸の開始

**手順**
1. 入力を検証する
2. 倉庫の存在を確認する。なければ404
3. その倉庫に実施中の棚卸がある場合は、409(`STOCKTAKE_IN_PROGRESS`)(案)
4. 棚卸を追加する(状態は `IN_PROGRESS`)
5. 倉庫に属するロケーション(削除済みを除く)の在庫行をすべて取得し、棚卸明細として追加する(帳簿数量 = 現在の在庫数量、実数量 = NULL)(案)
6. 保存する

**更新内容**

| テーブル | 操作 | 内容 |
|---|---|---|
| stocktakes | 追加 | `status` = IN_PROGRESS、`stocktake_date` |
| stocktake_lines | 追加(複数行) | `book_quantity` = 在庫数量、`actual_quantity` = NULL |

### 4.7 P07 実数量の入力

**手順**
1. 入力を検証する(0以上)
2. 棚卸と明細を取得する。明細が指定した棚卸のものでなければ404
3. 棚卸の状態が `IN_PROGRESS` であることを確認する。違えば409(`INVALID_STATE`)
4. 明細の実数量を更新して保存する

### 4.8 P08 棚卸の確定

**手順**
1. 棚卸を取得し、送られた `version` と比較する。違えば409(`VERSION_CONFLICT`)
2. 状態が `IN_PROGRESS` であることを確認する。違えば409(`INVALID_STATE`)
3. 実数量が未入力の明細がないことを確認する。あれば409(`INVALID_STATE`)(案)
4. 各明細の差異(実数量 − 帳簿数量)を求める
5. 差異が0でない明細について、次を行う
   1. 在庫行を取得する。在庫数量が帳簿数量と一致しない場合は、棚卸中に在庫が動いたことになるため、409(`INVALID_STATE`)として確定しない(案)
   2. 在庫数量を実数量に更新する
   3. 入出庫履歴を追加する
6. 棚卸の状態を `COMPLETED` にし、確定日時を設定する
7. 保存する(1つのトランザクション)

**更新内容**

| テーブル | 操作 | 内容 |
|---|---|---|
| stocks | 更新 | `quantity` = 実数量(差異があった行のみ) |
| stock_movements | 追加 | `movement_type` = STOCKTAKE_ADJUST、`quantity_change` = 差異、`remarks` に棚卸のID |
| stocktakes | 更新 | `status` = COMPLETED、`completed_at` = 現在日時 |

実数量が引当数量を下回る場合の扱いは未決(5章)。

### 4.9 P09 棚卸の中止

**手順**
1. 棚卸を取得し、送られた `version` と比較する。違えば409(`VERSION_CONFLICT`)
2. 状態が `IN_PROGRESS` であることを確認する。違えば409(`INVALID_STATE`)
3. 状態を `CANCELLED` にして保存する(在庫は変更しない)

### 4.10 P10〜P12 商品・倉庫・ロケーションの削除

**手順**
1. 対象を取得する。存在しない、または削除済みなら404
2. 在庫のチェックを行う。次の対象に、在庫数量または引当数量が0でない在庫行があれば、409(`HAS_STOCK`)
   - 商品: その商品の在庫行
   - ロケーション: そのロケーションの在庫行
   - 倉庫: 倉庫に属するロケーションの在庫行
3. `deleted_at` に現在日時を設定して保存する

在庫数量・引当数量がともに0の在庫行は、そのまま残す(履歴との整合のため)。

### 4.11 P13 マスタの登録・更新

**登録**
1. 入力を検証する
2. ロケーションの場合は、倉庫の存在を確認する。なければ404
3. コードの重複を確認する(削除済みも含む。ロケーションは同じ倉庫内)。重複なら409(`DUPLICATE_CODE`)
4. 追加して保存する。同時登録でユニーク制約に違反した場合も、409(`DUPLICATE_CODE`)

**更新**
1. 入力を検証する
2. 対象を取得する。なければ404
3. 送られた `version` と比較する。違えば409(`VERSION_CONFLICT`)
4. コード(ロケーションは倉庫も)は変更せず、それ以外の項目を更新して保存する(案)

### 4.12 P14 在庫の照会・集計

- 検索条件に応じて `stocks` を検索する。引当可能数は、在庫数量 − 引当数量で求める
- 集計は、`groupBy` が `product` なら商品ごとに全倉庫を合算し、`warehouse` なら商品 × 倉庫ごとにロケーションを合算する
- 削除済みの商品・ロケーションの在庫行は、結果に含めない(案)

### 4.13 P15 在庫下限アラートの検出

**手順**
1. 削除されておらず、在庫下限数量が設定されている商品を対象にする
2. 商品ごとに、全倉庫の在庫数量を合計する(在庫行がない商品は0とする)
3. 合計が在庫下限数量を下回る商品を返す。不足数は「在庫下限数量 − 合計」
4. 並び順は、不足数の大きい順(案)

### 4.14 P16 CSV出力

- 対応する検索APIと同じ絞り込み条件・並び順で、ページングを行わずに全件を出力する
- 文字コードはUTF-8(BOM付き)で、ヘッダ行を付ける(案)
- 件数が多い場合に備え、ストリーミングで返す(案)
