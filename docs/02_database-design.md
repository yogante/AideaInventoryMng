## 1. 概要



### 1.1 目的

本システムでは、商品・倉庫・ロケーション単位で在庫を管理し、入庫、出庫、在庫移動、棚卸などの業務処理を実現する。

## 2. データベース設計方針



### 2.1 命名規則



データベースのテーブル名・カラム名には `snake_case` を採用する。



| 対象 | 命名規則 | 例 |

|---|---|---|

| テーブル名 | snake_case・複数形 | products |

| カラム名 | snake_case | product_code |

| 主キー | id | id |

| 外部キー | 参照先テーブル名_id | product_id |

| 日時 | created_at / updated_at | created_at |

| 論理削除日時 | deleted_at | deleted_at |



C#側では `PascalCase` を使用し、EF CoreのマッピングによってDB側の命名規則に対応させる。



### 2.2 データ型



| 用途 | PostgreSQL型 | 備考 |

|---|---|---|

| 内部ID | bigint | IDENTITYによる自動採番 |

| コード | varchar | 最大文字数を指定 |

| 名称 | varchar | 最大文字数を指定 |

| 数量 | integer | 在庫・予約・棚卸数量 |

| バージョン | integer | 楽観的排他制御 |

| 日付 | date | 棚卸日など |

| 日時 | timestamptz | タイムゾーン付き日時 |

| 論理削除日時 | timestamptz | NULLの場合は有効 |



IDには `bigint GENERATED BY DEFAULT AS IDENTITY` を使用する。



日時はUTCを基準に保存し、画面表示時に必要なタイムゾーンへ変換する。



### 2.3 主キー・外部キー



- 各テーブルに内部管理用の主キー `id` を設定する。

- テーブル間の関連は外部キーで管理する。

- マスタデータの物理削除は原則禁止する。

- 履歴データを削除しない。

- 参照されているマスタの物理削除を防ぐため、外部キーの削除動作は原則RESTRICT相当とする。



### 2.4 論理削除



商品・倉庫・ロケーションのマスタテーブルには `deleted_at` を設ける。



- `deleted_at IS NULL`：有効

- `deleted_at IS NOT NULL`：削除済み



削除済みデータもDB上に保持する。



コードの一意性は削除済みデータを含めて維持し、過去に使用したコードを再利用できないようにする。



### 2.5 排他制御



同時更新によるデータ不整合を防ぐため、`version` 整数列を使用した楽観的排他制御を採用する。



対象テーブル：

- products

- stocks



仕様：

- `version` の初期値は1とする。

- 更新時にアプリケーション側で1増加させる。

- UPDATE時には更新前のversionを条件に含める。

- 更新件数が0件の場合は競合と判断する。

- EF CoreではConcurrency Tokenとして設定する。

- 競合発生時は `DbUpdateConcurrencyException` を捕捉する。



### 2.6 在庫数量の管理



在庫は「商品 × ロケーション」単位で管理する。



- `quantity`：現在の実在庫数量

- `reserved_quantity`：出庫予定として確保済みの数量

- `available_quantity`：出庫可能数量



出庫可能数量は以下で算出する。



`available_quantity = quantity - reserved_quantity`



`available_quantity` はDBに保存せず、計算によって取得する。



在庫数量と予約数量には以下の制約を設ける。



- quantity >= 0

- reserved_quantity >= 0

- reserved_quantity <= quantity



### 2.7 在庫更新と履歴登録



在庫数量の変更と入出庫履歴の登録は、必ず同一トランザクションで実行する。



在庫更新に成功しても履歴登録に失敗した場合、トランザクション全体をロールバックする。



入出庫履歴は原則として更新・削除しない。訂正が必要な場合は、訂正内容を反映した新しい履歴を追加する。



### 2.8 棚卸中の入出庫制御



棚卸中の在庫変動を防ぐため、棚卸対象ロケーションの入出庫・在庫移動を制限する。



棚卸開始から完了まで、対象ロケーションについて以下を禁止する。



- 入庫

- 出庫

- 在庫移動の移動元としての利用

- 在庫移動の移動先としての利用

- その他の在庫数量変更処理



棚卸完了または取消後に制限を解除する。



入出庫処理と棚卸処理の間で競合が発生しないよう、PostgreSQLの行ロックとトランザクションを利用して制御する。

- 入庫・出庫・在庫移動など、在庫数量を変更する処理は、対象ロケーションの行を `SELECT ... FOR UPDATE` でロックしてから棚卸状態を確認する。
- 棚卸開始処理も、棚卸対象ロケーションの行を同じ方法でロックしてから棚卸状態を `IN_PROGRESS` に変更する。
- 複数ロケーションをロックする場合は、ロケーションIDの昇順でロックを取得し、デッドロックの発生を抑制する。
- ロック取得後に棚卸状態を確認し、棚卸中であれば在庫変更処理を中止する。
- 棚卸完了・取消処理もトランザクション内で実行し、状態変更とロック解除を整合させる。

これにより、棚卸開始と入出庫処理が同時に実行された場合も、同じロケーション行のロックによって処理を直列化する。



## 2.9 監査カラムの共通ルール

テーブルの用途に応じて、監査カラムを以下の3種類に分類する。

**マスタテーブル（products、warehouses、locations）**

- `created_at`：作成日時。NOT NULL。
- `updated_at`：最終更新日時。NOT NULL。
- `created_by`：作成者ID。NULL許容。
- `updated_by`：最終更新者ID。NULL許容。
- `deleted_at`：論理削除日時。NULL許容。

**業務データテーブル（stocks、stocktakes、stocktake_lines）**

- `created_at`：作成日時。NOT NULL。
- `updated_at`：最終更新日時。NOT NULL。
- `created_by`：作成者ID。NULL許容。
- `updated_by`：最終更新者ID。NULL許容。
- `deleted_at` は設けない。

**履歴テーブル（stock_movements）**

- `created_at`：履歴登録日時。NOT NULL。
- `created_by`：登録者ID。NULL許容。
- 登録後の更新・削除を行わないため、`updated_at`、`updated_by`、`deleted_at` は設けない。

日時はUTCを基準に `timestamptz` で保存する。`created_at` は登録時に設定し、その後変更しない。`updated_at` はレコード更新時に必ず更新する。

`created_by` と `updated_by` は将来のユーザー管理機能に備えて設ける。現時点ではユーザーテーブルを作成しないため、外部キー制約は設定せず、NULLを許容する。

マスタの論理削除は `deleted_at` によって管理する。業務データおよび履歴データには論理削除カラムを設けない。

## 5. テーブル定義



### 5.1 products（商品マスタ）



商品情報を管理する。



| No | カラム名 | 論理名 | データ型 | NULL | キー | デフォルト | 説明 |

|---|---|---|---|---|---|---|---|

| 1 | id | 商品ID | bigint | NOT NULL | PK | IDENTITY | 内部管理用ID |

| 2 | product_code | 商品コード | varchar(50) | NOT NULL | UK | - | 商品を識別するコード |

| 3 | name | 商品名 | varchar(200) | NOT NULL | - | - | 商品名称 |

| 4 | unit | 単位 | varchar(20) | NOT NULL | - | - | 個、箱など |

| 5 | min_stock_quantity | 最低在庫数量 | integer | NULL | - | NULL | 在庫不足判定数量 |

| 6 | version | バージョン | integer | NOT NULL | - | 1 | 楽観的排他制御 |

| 7 | created_at | 作成日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 作成日時 |

| 8 | updated_at | 更新日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 更新日時 |

| 9 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 10 | updated_by | 更新者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 11 | deleted_at | 削除日時 | timestamptz | NULL | - | NULL | 論理削除日時 |



制約：

- `product_code` は一意とする。削除済み商品も含めて重複を禁止する。

- `min_stock_quantity` はNULLまたは0以上とする。

- `version` は1以上とする。



在庫不足判定：

- `min_stock_quantity` がNULLの場合はアラート対象外。

- 商品の全ロケーション・全倉庫の在庫数量を合計し、最低在庫数量を下回った場合にアラート対象とする。



### 5.2 warehouses（倉庫マスタ）



倉庫情報を管理する。



初期データとして東京倉庫・大阪倉庫を登録する予定。



| No | カラム名 | 論理名 | データ型 | NULL | キー | デフォルト | 説明 |

|---|---|---|---|---|---|---|---|

| 1 | id | 倉庫ID | bigint | NOT NULL | PK | IDENTITY | 内部管理用ID |

| 2 | warehouse_code | 倉庫コード | varchar(20) | NOT NULL | UK | - | 倉庫識別コード |

| 3 | name | 倉庫名 | varchar(100) | NOT NULL | - | - | 倉庫名称 |

| 4 | created_at | 作成日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 作成日時 |

| 5 | updated_at | 更新日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 更新日時 |

| 6 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 7 | updated_by | 更新者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 8 | deleted_at | 削除日時 | timestamptz | NULL | - | NULL | 論理削除日時 |



制約：

- `warehouse_code` は一意とする。削除済み倉庫も含めて重複を禁止する。

- 倉庫に所属するロケーションが存在する場合、物理削除を禁止する。





### 5.3 locations（ロケーションマスタ）



倉庫内の保管場所を管理する。



| No | カラム名 | 論理名 | データ型 | NULL | キー | デフォルト | 説明 |

|---|---|---|---|---|---|---|---|

| 1 | id | ロケーションID | bigint | NOT NULL | PK | IDENTITY | 内部管理用ID |

| 2 | warehouse_id | 倉庫ID | bigint | NOT NULL | FK | - | 所属する倉庫 |

| 3 | location_code | ロケーションコード | varchar(30) | NOT NULL | UK | - | 倉庫内の識別コード |

| 4 | name | ロケーション名 | varchar(100) | NOT NULL | - | - | 保管場所名称 |

| 5 | created_at | 作成日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 作成日時 |

| 6 | updated_at | 更新日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 更新日時 |

| 7 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 8 | updated_by | 更新者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 9 | deleted_at | 削除日時 | timestamptz | NULL | - | NULL | 論理削除日時 |



外部キー：

- `warehouse_id` → `warehouses.id`



制約：

- `(warehouse_id, location_code)` の複合ユニーク制約を設定する。

- 同一倉庫内でロケーションコードの重複を禁止する。

- 削除済みロケーションも含めてコードの再利用を禁止する。

- 在庫または入出庫履歴から参照されているロケーションの物理削除を禁止する。



### 5.4 stocks（在庫）



商品・ロケーション単位の現在在庫数量を管理する。



| No | カラム名 | 論理名 | データ型 | NULL | キー | デフォルト | 説明 |

|---|---|---|---|---|---|---|---|

| 1 | id | 在庫ID | bigint | NOT NULL | PK | IDENTITY | 内部管理用ID |

| 2 | product_id | 商品ID | bigint | NOT NULL | FK | - | 商品 |

| 3 | location_id | ロケーションID | bigint | NOT NULL | FK | - | 保管場所 |

| 4 | quantity | 在庫数量 | integer | NOT NULL | - | 0 | 現在の実在庫 |

| 5 | reserved_quantity | 予約数量 | integer | NOT NULL | - | 0 | 出庫予約済み数量 |

| 6 | version | バージョン | integer | NOT NULL | - | 1 | 楽観的排他制御 |

| 7 | created_at | 作成日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 作成日時 |

| 8 | updated_at | 更新日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 更新日時 |

| 9 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 10 | updated_by | 更新者ID | bigint | NULL | - | NULL | 将来のユーザーID |



外部キー：

- `product_id` → `products.id`

- `location_id` → `locations.id`



制約：

- `(product_id, location_id)` に複合ユニーク制約を設定する。

- `quantity >= 0`

- `reserved_quantity >= 0`

- `reserved_quantity <= quantity`

- `version >= 1`



運用方針：

- 在庫が0になってもレコードは原則削除しない。

- 在庫数量の変更は入庫・出庫・移動・棚卸調整などの業務処理を通じて実施する。

- 予約数量の変更は実在庫数量を変更しない。

- 出庫可能数量は `quantity - reserved_quantity` で算出する。



### 5.5 stock_movements（入出庫履歴）



在庫数量が変動した際の履歴を管理する。



本テーブルは監査・追跡のための履歴テーブルとし、登録後の更新・削除は原則禁止する。



| No | カラム名 | 論理名 | データ型 | NULL | キー | デフォルト | 説明 |

|---|---|---|---|---|---|---|---|

| 1 | id | 履歴ID | bigint | NOT NULL | PK | IDENTITY | 内部管理用ID |

| 2 | product_id | 商品ID | bigint | NOT NULL | FK | - | 対象商品 |

| 3 | location_id | ロケーションID | bigint | NOT NULL | FK | - | 対象ロケーション |

| 4 | movement_type | 入出庫種別 | varchar(30) | NOT NULL | - | - | 入出庫・移動・棚卸調整 |

| 5 | quantity_change | 数量変動 | integer | NOT NULL | - | - | 増減数量 |

| 6 | transfer_no | 移動番号 | bigint | NULL | - | NULL | 移動元・移動先の共通番号 |

| 7 | occurred_at | 発生日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 業務上の発生日時 |

| 8 | remarks | 備考 | varchar(200) | NULL | - | NULL | 補足情報 |

| 9 | created_at | 作成日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 登録日時 |

| 10 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |



外部キー：

- `product_id` → `products.id`

- `location_id` → `locations.id`



入出庫種別：



| 種別 | 内容 | quantity_change |

|---|---|---|

| RECEIPT | 入庫 | 正数 |

| ISSUE | 出庫 | 負数 |

| TRANSFER_OUT | 移動元からの出庫 | 負数 |

| TRANSFER_IN | 移動先への入庫 | 正数 |

| STOCKTAKE_ADJUST | 棚卸差異調整 | 正数または負数 |



制約：

- `quantity_change <> 0`

- `movement_type` は定義済みの種別のみ許可する。

- RECEIPT、TRANSFER_INは正数とする。

- ISSUE、TRANSFER_OUTは負数とする。

- STOCKTAKE_ADJUSTは正数または負数とする。



在庫移動の処理：

- 移動元に `TRANSFER_OUT` を登録する。

- 移動先に `TRANSFER_IN` を登録する。

- 両方の履歴に同じ `transfer_no` を設定する。

- 移動元・移動先の在庫更新と2件の履歴登録を同一トランザクションで実施する。



`transfer_no` はシーケンス等を利用して採番する。



履歴訂正：

- 登録済み履歴の直接更新・削除は行わない。

- 誤登録があった場合は、訂正を表す新しい履歴を追加する。

| 6 | updated_at | 更新日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 更新日時 |

| 7 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| status | 内容 |

### 5.7 stocktake_lines（棚卸明細）



棚卸対象の商品・ロケーションごとの帳簿数量、実在庫数量、差異数量を管理する。



| No | カラム名 | 論理名 | データ型 | NULL | キー | デフォルト | 説明 |

|---|---|---|---|---|---|---|---|

| 1 | id | 棚卸明細ID | bigint | NOT NULL | PK | IDENTITY | 内部管理用ID |

| 2 | stocktake_id | 棚卸ID | bigint | NOT NULL | FK | - | 棚卸ヘッダー |

| 3 | product_id | 商品ID | bigint | NOT NULL | FK | - | 対象商品 |

| 4 | location_id | ロケーションID | bigint | NOT NULL | FK | - | 対象ロケーション |

| 5 | book_quantity | 帳簿数量 | integer | NOT NULL | - | - | 棚卸開始時点の在庫 |

| 6 | actual_quantity | 実在庫数量 | integer | NULL | - | NULL | 実際に数えた数量 |

| 7 | difference_quantity | 差異数量 | integer | NULL | - | NULL | 実在庫と帳簿数量の差 |

| 8 | created_at | 作成日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 作成日時 |

| 9 | updated_at | 更新日時 | timestamptz | NOT NULL | - | CURRENT_TIMESTAMP | 更新日時 |

| 10 | created_by | 作成者ID | bigint | NULL | - | NULL | 将来のユーザーID |

| 11 | updated_by | 更新者ID | bigint | NULL | - | NULL | 将来のユーザーID |



外部キー：

- `stocktake_id` → `stocktakes.id`

- `product_id` → `products.id`

- `location_id` → `locations.id`



制約：

- `(stocktake_id, product_id, location_id)` に複合ユニーク制約を設定する。

- `book_quantity >= 0`

- `actual_quantity` はNULLまたは0以上とする。

- `difference_quantity` はNULLまたは正数・0・負数を許可する。負数を許容するため、0以上のCHECK制約は設定しない。
- `difference_quantity` がNULL以外の場合、`actual_quantity` はNULL不可とし、`difference_quantity = actual_quantity - book_quantity` を満たす。



差異数量の計算：



`difference_quantity = actual_quantity - book_quantity`



棚卸開始時に帳簿数量を取得して保存する。



実在庫数量が入力されるまでは `actual_quantity` と `difference_quantity` をNULLとする。



棚卸完了時に差異数量を計算し、差異がある場合は `stock_movements` に `STOCKTAKE_ADJUST` を登録する。

## 6. 業務処理とデータ更新



### 6.1 入庫



1. 商品・ロケーションが有効であることを確認する。

2. 対象ロケーションが棚卸中でないことを確認する。

3. 在庫レコードを取得する。

4. 在庫数量に入庫数量を加算する。

5. `RECEIPT` の履歴を登録する。

6. 同一トランザクションでコミットする。



### 6.2 出庫



1. 商品・ロケーションが有効であることを確認する。

2. 対象ロケーションが棚卸中でないことを確認する。

3. 在庫レコードを取得する。

4. 出庫可能数量を確認する。

5. 在庫数量から出庫数量を減算する。

6. `ISSUE` の履歴を登録する。

7. 同一トランザクションでコミットする。



出庫数量が出庫可能数量を超える場合は処理を禁止する。



### 6.3 在庫移動



1. 移動元・移動先のロケーションが有効であることを確認する。

2. 移動元・移動先が棚卸中でないことを確認する。

3. 移動元の出庫可能数量を確認する。

4. 移動元の在庫数量を減算する。

5. 移動先の在庫数量を加算する。

6. 移動元に `TRANSFER_OUT` を登録する。

7. 移動先に `TRANSFER_IN` を登録する。

8. 両方の履歴に同一の `transfer_no` を設定する。

9. 同一トランザクションでコミットする。



移動元と移動先が同一ロケーションの場合は処理を禁止する。



### 6.4 棚卸



1. 棚卸ヘッダーを作成する。

2. 棚卸対象ロケーションを決定する。

3. 対象ロケーションの入出庫・在庫移動を制限する。

4. 棚卸開始時点の帳簿数量を明細に保存する。

5. 実在庫数量を入力する。

6. 差異数量を計算する。

7. 差異がある場合は `STOCKTAKE_ADJUST` の履歴を登録する。

8. 在庫数量を実在庫数量に合わせて更新する。

9. 棚卸状態を `COMPLETED` に変更する。

10. 入出庫制限を解除する。



棚卸完了時の在庫更新、履歴登録、棚卸状態変更は同一トランザクションで実施する。



棚卸を取り消す場合は、在庫調整を実施せず、状態を `CANCELLED` に変更して制限を解除する。

## 8. データ整合性・運用ルール



### 8.1 在庫数量の整合性



在庫数量は入庫・出庫・移動・棚卸調整の履歴と整合するように管理する。



初期在庫については入庫処理によって登録する。



### 8.2 外部キーの削除制御



商品・倉庫・ロケーションが履歴や在庫から参照されている場合、物理削除は行わない。



マスタの削除は論理削除で対応する。



### 8.3 予約数量



予約数量の増減は実在庫数量に影響させない。



予約数量を超える出庫や、実在庫数量を超える予約は許可しない。



予約の詳細な明細管理や注文との紐付けは、将来の拡張対象とする。



### 8.4 ユーザーID



`created_by`、`updated_by` は将来のユーザー管理機能を想定して設ける。



現時点ではユーザーテーブルを作成しないため、外部キー制約は設定しない。
