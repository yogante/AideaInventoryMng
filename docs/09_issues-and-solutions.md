## 1. 概要

### 1.1 目的

開発中に発生した問題と、その原因・解決方法・学びを記録する。再発を防ぐとともに、最終学習報告書と動作検証報告書の材料にする。

### 1.2 運用

- 問題が起きたら、その場で第3章の一覧に1行追加し、詳細を書く(後でまとめて書かない)
- 解決したら、状況を更新し、解決方法と学びを書く
- Day 19に、全体を整理して最終学習報告書に反映する

---

## 2. 記録のルール

| 項目 | 内容 |
|---|---|
| ID | `I` + 3桁の連番(I001、I002 …) |
| 区分 | 設計、実装、環境(Docker)、AWS、テスト、運用、その他 |
| 状況 | 未対応、対応中、解決済み、保留 |
| エラーメッセージ | 要約せず、原文のまま貼る |

| 学び・再発防止 | 次に同じ問題を避けるための気づきを書く |

### 3.2 詳細

#### I001 設計書の確定後、既存のマイグレーション・DBが設計と合わなくなった

| 項目 | 内容 |
|---|---|
| 区分 | 設計 |
| 症状 | DB設計書で決めた内容(snake_caseの命名規則、7テーブル構成、共通列)と、すでに作成済みのマイグレーション・DBが一致しない |
| 原因 | 設計書を確定する前に、先にマイグレーションを作成していた |
| 解決方法 | 既存のDBを削除し(`dotnet ef database drop`)、`Migrations` フォルダを削除したうえで、設計書に合わせたエンティティから初期マイグレーションを作り直す |
| 学び・再発防止 | 設計を先に確定してから、マイグレーションを作る。設計書を正とし、コードを設計書に合わせる |
| 状況 | 対応中 |

#### I002 ドキュメントの番号04が重複した

| 項目 | 内容 |
|---|---|
| 区分 | その他 |
| 症状 | `docs` の番号04が、Docker環境構築手順書と処理設計書の2つで重なった |
| 原因 | 当初の成果物一覧になかった処理設計書を、後から追加したため |
| 解決方法 | 処理設計書を04とし、以降を05〜10に繰り下げた。READMEと01の一覧を更新した |
| 学び・再発防止 | 成果物を追加するときは、番号と一覧(READMEと01の7章)を同時に更新する |
| 状況 | 解決済み(2026-11-12) |

#### I003 設計書(02・03・04)の間に不一致が見つかった

| 項目 | 内容 |
|---|---|
| 区分 | 設計 |
| 症状 | DB設計書・API設計書・処理設計書の間で、次の不一致があった。`version` を持つテーブルの範囲、棚卸中の制限範囲(ロケーション単位か倉庫単位か)、`stocktakes` の列(`completed_at`・`remarks`・`version`)、API一覧とエラーコード表への棚卸APIの未反映、商品(説明・価格)・倉庫(住所・備考)・ロケーション名の項目、関連ドキュメントの旧番号、Markdownの表の崩れ |
| 原因 | 棚卸の処理を分割・改訂したときなど、資料を別々に更新し、影響する他の資料を確認しなかった |
| 解決方法 | 02・03・04・09を揃えて改訂した。`version` を warehouses・locations・stocktakes にも追加し、棚卸中の制限を倉庫単位に統一した。API一覧・エラーコード表・各項目を更新し、番号と表の崩れを直した |
| 学び・再発防止 | 設計を変更したら、DB設計書、API設計書、処理設計書の順に影響範囲を確認し、各資料の変更履歴に影響先を書く。更新後は、資料間で用語・列名・コード・数値を突き合わせる |
| 状況 | 解決済み(2026-11-18) |

## 4. 既知の制約(設計時点)

設計の段階で、完全には防げない、または実装時の検証が必要と判断した事項。テストで挙動を確認し、結果を動作検証報告書に記載する。

| ID | 内容 | 現在の対応 | 確認する時期・方法 | 参照 |
|---|---|---|---|---|
| K01 | 棚卸の開始と入出庫が同時に重なると、帳簿数量と在庫がずれる可能性がある | 対応済み(設計)。在庫を変更する処理は、ロケーション行を `SELECT ... FOR UPDATE` でロックしてから棚卸状態を確認する。棚卸の確定時にも、在庫数量と帳簿数量の一致を確認する | 結合テスト(Day 17)で、ロック待ちによる直列化と、確定時の一致確認を検証する | 04の2.7、02の2.8 |
| K02 | 商品の削除は行ロックを取らないため、在庫チェックと入庫が短い間に重なると、削除済みの商品に在庫が残る可能性がある | 今回は許容する。ロケーション・倉庫の削除は、ロケーション行のロックで対応する | 結合テスト(Day 17)で再現を確認する | 04の4.12、5.1 |
| K03 | 競合時の再試行は最大3回。超えた場合は409を返す | 3回で打ち切る。ロックを取らない更新(マスタの更新、棚卸ヘッダーの `version` 比較)では `version` による競合検出を維持する | 排他制御の検証(Day 10)で、回数の妥当性を確認する | 04の2.4 |
| K04 | ロックの取得順序を守らない処理があると、デッドロックが起きる可能性がある | 取得順序を「ロケーション行(IDの昇順) → 棚卸ヘッダー行 → 在庫行(IDの昇順)」に統一する | 同時実行テスト(Day 13、Day 17)で確認する | 04の2.7、02の2.8 |
